第一次尝试的起跑门槛等待 180 秒后超时：CPU 2 / CPU 7 的频率上限分别为 2,630,400 / 2,169,600 kHz，协议要求两者均不低于 2,630,400 kHz。退出时电池温度为 32.5°C，设备亮屏、未锁定，基准 app 位于前台。记录仅能确认频率上限不满足协议，不能据此确定系统限频原因。

第二次尝试复用相同二进制及协议。退出快照仍为亮屏、未锁定，但 `focused_package` 为 `null`，无法确认基准 app 前台，故 `gate_wait_s` 为 `-2`。当时 CPU 2 / CPU 7 上限为 2,572,800 / 1,939,200 kHz，电池温度为 33.7°C。不能将此退出原因记作频率等待超时，也不能仅凭空前台字段断言发生了锁屏或 app 崩溃。

采集器待改进项：CPU 亲和性 `7c` 只覆盖 CPU 2–6，起跑门槛却监测 CPU 2 / 7，未直接覆盖 CPU 5–6 所属频率策略。本次未更改此规则；后续若调整，需明确记录协议变化并重新配对测量，不能覆盖既有场次。

这两份失败记录的检查器退出码为 `2`（数据不完整）。JSON 的 `report_kind: full` 表示计划运行完整清单，不代表测试完成。缺失性能值不填零，不计算倍率；项目 README 的小米 14 对照来自另存的[动态调频场次](ungated/README.md)，不使用这两份记录。
