### 历史趋势：v0.1.0 → 当前 v0.3.0

小米 10、相同 200 行语料与模型、各自默认单线程参数。下表是 **2026-09-05 与 09-07 两次测量的跨场次汇总**，不是新做的 v0.1.0/v0.3.0 配对实验。v0.3.0 的引擎源码对应关系见其版本说明。

| 场景 | v0.1.0 首次速度 | v0.3.0 参考速度 | 速度倍率 / 提升 | 峰值 RSS | 内存减少 |
|---|---:|---:|---:|---:|---:|
| 英→中 | 27.75 条/秒 | 47.09 条/秒 | 1.70× / +69.7% | 323 → 184 MiB | 42.9% |
| 日→英→中 | 12.44 条/秒 | 23.09 条/秒 | 1.86× / +85.6% | 483 → 289 MiB | 40.2% |

速度由同一批 200 条源文的原始耗时换算，首次速度包含服务/模型加载，不是热态纯推理速度。源数据为 [v0.1.0 样本](v0.2.0/results.json) 的 `enzh_w1` / `pivot_w1` 和 [v0.3.0 参考样本](v0.3.0/results-mi10.json) 的 `main: enzh_b512p` / `pivot_b512p`。默认参数已变化，因此包含参数优化收益，不能解释为纯内核加速。

### 速度展示口径

- 翻译速度（条源文/秒）= `输入条数 × 1000 / 耗时中位数 ms`。这里的条数是输入列表长度，不是分句后的句子数或输出 token 数；仅在相同语料、相同计时范围内比较。
- 速度倍率 = `新版速度 / 旧版速度` = `旧版耗时 / 新版耗时`；速度提升 = `(倍率 − 1) × 100%`。例如耗时 10 s → 5 s，速度是原来的 2 倍、提升 100%，不是提升 50%。
- 内存降低仍按 `1 − 新版 RSS / 旧版 RSS` 计算。所有百分比从未舍入的原始中位数计算，最后才格式化，不能把阶段百分比相加。
- 这只是同一测量结果的展示换算，**不改八场景、原始毫秒字段、计时窗口或清单 ID**。首次速度与热态速度分开列；原有耗时表保留供审计。

## 固定测量口径

正式比较统一使用 [`android-native-v1`](../tools/version-bench/suites/android-native-v1.json)，不再每个版本自行挑选场景。每台固定设备保留下面 8 行，列顺序固定为 **首次耗时 ms、热态耗时 ms、首遍峰值 RSS MiB**，同时记录输出哈希、完成状态和原始数据链接。

| 固定场景 ID | 语向 | 执行方式 | batch words | 英文前缀表 |
|---|---|---|---:|---|
| `enzh_w1` | 英→中 | Async，1 worker | 1024 | 关 |
| `enzh_w2` | 英→中 | Async，2 workers | 1024 | 关 |
| `enzh_w4` | 英→中 | Async，4 workers | 1024 | 关 |
| `pivot_w1` | 日→英→中 | Async，1 worker | 1024 | 关 |
| `enzh_b512p` | 英→中 | Blocking，单线程 | 512 | 开 |
| `pivot_b512p` | 日→英→中 | Blocking，单线程 | 512 | 开 |
| `enzh_w2_512p` | 英→中 | Async，2 workers | 512 | 开 |
| `pivot_w2_512p` | 日→英→中 | Async，2 workers | 512 | 开 |

这张清单固定保留历史八场景，不随库的默认参数改变。`w*` 是 native AsyncService 逐条提交路径，不代表 AAR 批量 API；以后补测 AAR 或交互单句时，新增独立场景，不能替换现有行。

- 每场景、每版本 **3 个独立进程**，按 AB / BA / AB 交错运行；每进程 3 遍，结果缓存关闭。
- 首次耗时包含服务创建、模型创建/懒加载和首遍翻译；不含下载、进程启动或 JNI。未清空系统文件缓存，不称为“冷磁盘启动”。
- 热态耗时先取每进程后两遍的中位数，再取三进程中位数。首次峰值内存取首遍后 VmHWM（KiB ÷ 1024），不能与 app PSS 相减。
- 同配置回归比较必须使用同一台设备、系统版本、模型/词表/shortlist/前缀表、语料、编译工具链、harness、CPU 亲和性和参数。不同手机分开建基线。
- 记录起止温度与频率上限。起跑前等待恢复；门槛超时就中止，保留部分结果。它不等于锁定实际 CPU 频率。
- 失败、超时、译文变化都不能删除或当成零耗时。性能通过不代表质量通过；另跑哈希与必要的质量评测。

### 维度只能追加，不能悄悄替换

- 每版沿用同一份[报告模板](TEMPLATE.md)。缺失项标 `未测`，无法运行标 `不支持`，崩溃标 `失败`；保留原行，不填 0，不删行凑齐对比。存在缺项时不能标为完整验收通过。
- 后续新增设备、语向、输入长度、线程档位、指标等，升级测试清单 ID，并保留旧清单文件；已有场景 ID、定义、单位与统计方法不变。新指标需要同时实现采集、检查和展示，不能只加一个标题。
- 扩展后给历版表格追加相同的新行/列。旧版本的新项先标 `未测`，有条件时重跑旧版本补齐；对比不能拿旧场景替代新场景。
- 更换模型、语料、harness 或计时口径属于**新的可比数据组**，不是覆盖旧数字。要得出两版差值，需在新条件下重新配对测量，保留旧记录。
- “各版本默认参数收益”单独附表。主比较始终按相同场景 ID 对齐，不能拿旧版 1024/async 与新版 512/blocking 当作同配置回归。

## 新增一次测量

完整构建、设备文件准备、运行命令见 [工具说明](../tools/version-bench/README.md)。默认运行完整八场景；指定 `--scenarios` 仅作探索，不能作为正式基线。每次使用新的输出文件名，不覆盖已归档结果。建议按下列结构保存：

```text
benchmarks/vX.Y.Z/
  README.md                       # 结论、版本/提交、与上一版差异、局限
  results-<device>-<date>.json     # 原始逐轮样本、构建记录、输入指纹、失败信息
  summary-<device>-<date>.json     # 可选派生汇总，必须能从 raw 重新生成
```

本地代码用 `--working-tree-version v0.3.0` 命名快照，工具记录 HEAD、未提交状态和原生源码摘要，不要求先提交或打 tag。发布前再核对最终 tag 与被测源码，不能只改 JSON 中的版本名。

## 回归检查

```bash
python3 tools/version-bench/check.py baseline.json candidate.json \
  --baseline-version v0.3.0 --candidate-version candidate
```

同一份配对报告也可作为两个文件参数。检查器先核对测试清单 ID/摘要、完整八场景和固定重复协议；即使双方同时漏掉同一场景，也不能通过。输出以首次/热态速度（条源文/秒、倍率、变化百分比）展示，并附原始耗时。判定仍沿用原门槛：首次/热态耗时和峰值 RSS 任一增加 **超过 10%** 则失败；耗时 +10% 等价于速度约 −9.09%，没有将它悄悄改成速度 −10%。可用 `--latency-pct`、`--memory-pct` 调整。三个耗时/RSS 样本的极差超过中位数 10%，或起跑电池温度范围超过 3°C，要求复测，不给通过结论。阈值是初始报警线，不是统计显著性检验，也不保证检出小幅回归。

退出码：`0` = 条件匹配且未越线；`1` = 性能越线或稳定译文哈希变化；`2` = 数据不完整、崩溃、条件不匹配或噪声过大。**1 和 2 都应阻止将这次结果标为验收通过。**

现有历史 JSON 原样保留，部分缺少设备、模型或构建指纹，检查器会返回 `2`。需要用新版工具补测一次，才能建立完整的自动回归基线，不凭空补写历史元数据。共享 CI 仅运行检查器单元测试；真机性能验收需在固定设备上手动运行，尚未接入自动设备流水线。
