# 版本性能基准

这里保存每个版本的测量结果、条件和失败记录，用于展示优化进展，也用于发现后续回归。最新归档为 **v0.5.0 发布前测量**；发布前测量的快照标签、提交及源码摘要保持原样，不能仅凭标签判断测量对象。

## 目录结构

```text
benchmark/
  app/                 # 真机基准 App（Gradle 模块 :benchmark-app）
  data/
    README.md          # 本页：版本索引、固定口径、回归规则
  TEMPLATE.md          # 新版本报告模板
  CITATION.md          # FLORES-200 数据出处与引用
  shared/              # 跨版本共用、只保存一份
    MANIFEST.json      #   每个共享文件的 sha256 与来源版本
    collectors/        #   采集程序、测试入口、测试清单
    corpora/           #   FLORES-200 切片与参考译文
    archive.py         #   供各版本 checks/ 解析路径
  vX.Y.Z/
    README.md          # 唯一叙述文件：与上个版本的差异与对比
    index.json         # 机器可读索引：测量项、状态、数据位置、共享文件别名
    raw/               # 原始记录（逐进程样本、译文、评分、指纹、日志）
    checks/            # 离线复核脚本
    verify.py          # 复核入口
```

两条存储规则：

- **原始记录不改写。** 归档 JSON 保持采集时的字节，包括其中记录的文件名。
- **相同字节只存一份。** 多个版本共用的采集程序与语料放在 `shared/`，各版本 `index.json` 的 `collectors` / `corpora` 记录别名；同一次评测中输出完全相同的译文按内容保存一份，文件名取 `output_sha256` 前 8 位，清单仍逐条记录版本、语向和轮次。复核脚本用记录里已有的 sha256 定位文件，因此去重不削弱任何校验。

少数重复是有意保留的：冻结的 App 检查器要求源码指纹与报告同目录，删除会让归档无法独立复核，这类文件在相关版本的 `index.json` 的 `retained_duplicate` 中注明。

## 历史趋势：v0.1.0 → v0.3.0

小米 10、相同 200 行语料与模型、各自默认单线程参数。下表汇总不同批次的历史测量，仅用于趋势参考；v0.3.0 的源码对应关系见其版本说明。

| 场景 | v0.1.0 首次速度 | v0.3.0 参考速度 | 速度倍率 / 提升 | 峰值 RSS | 内存减少 |
|---|---:|---:|---:|---:|---:|
| 英→中 | 27.75 条/秒 | 47.09 条/秒 | 1.70× / +69.7% | 323 → 184 MiB | 42.9% |
| 日→英→中 | 12.44 条/秒 | 23.09 条/秒 | 1.86× / +85.6% | 483 → 289 MiB | 40.2% |

速度由同一批 200 条源文的原始耗时换算，首次速度包含服务/模型加载，不是热态纯推理速度。源数据为 [v0.1.0 样本](v0.2.0/raw/results.json) 的 `enzh_w1` / `pivot_w1` 和 [v0.3.0 参考样本](v0.3.0/raw/mi10/results.json) 的 `main: enzh_b512p` / `pivot_b512p`。默认参数已变化，因此包含参数优化收益，不能解释为纯内核加速。

### 统计口径

速度为 `输入条数 × 1000 / 耗时中位数 ms`，条数指源文列表长度。首次和热态分别统计；速度倍率为 `新版速度 / 旧版速度`，RSS 减少为 `1 − 新版 RSS / 旧版 RSS`。百分比从未舍入的数据计算。原生 RSS 与 App PSS 分别展示。

## 采集与展示分离

每个版本只按固定协议采集当前版并归档，不为每张表重跑测试。README、版本对比、发布说明从版本 `index.json` 指定的原始文件生成，旧版直接使用已有归档。入口见[统一生成器](../../tools/benchmark-report/README.md)。缺项或测试条件变化明确标注，补测需要单独请求。

## 固定测量口径

后续常规比较默认使用 [`android-native-v2`](../../tools/version-bench/suites/android-native-v2.json)，保留下表除 `enzh_w4` 外的 7 行；历史 [`android-native-v1`](shared/collectors/suites/android-native-v1.json) 的 8 行及已归档数据保持不变，列顺序固定为 **首次耗时 ms、热态耗时 ms、首遍峰值 RSS MiB**，同时记录输出哈希、完成状态和原始数据链接。

| 固定场景 ID | 语向 | 执行方式 | batch words | 英文前缀表 |
|---|---|---|---:|---|
| `enzh_w1` | 英→中 | Async，1 worker | 1024 | 关 |
| `enzh_w2` | 英→中 | Async，2 workers | 1024 | 关 |
| `enzh_w4` | 英→中 | Async，4 workers | 1024 | 关 |
| `pivot_w1` | 日→英→中 | Async，1 worker | 1024 | 关 |
| `enzh_b512p` | 英→中 | Blocking，单线程 | 512 | 开 |
| `pivot_b512p` | 日→英→中 | Blocking，单线程 | 512 | 开 |
| `enzh_w2_512p` | 英→中 | Async，2 workers | 512 | 开 |
| `pivot_w2_512p` | 日→英→中 | Async，2 workers | 512 | 开 |

v2 仅取消四线程常规复测，其余输入、线程、配置、重复次数和指标不变。App 对应采用 `android-app-v2` 六场景（英→中、日→中各 ML Kit / 单线程 / 双线程）；历史 App v1 八场景保留。场景清单不随产品默认参数隐式改变。`w*` 是 native AsyncService 逐条提交路径，不代表 AAR 批量 API；以后补测 AAR 或交互单句时，新增独立场景，不能替换现有行。

- 每场景、每版本 **3 个独立进程**，常规采集只运行当前版本；显式配对重测才按 AB / BA / AB 交错运行。每进程 3 遍，结果缓存关闭。
- 首次耗时包含服务创建、模型创建/懒加载和首遍翻译；不含下载、进程启动或 JNI。未清空系统文件缓存，不称为“冷磁盘启动”。
- 热态耗时先取每进程后两遍的中位数，再取三进程中位数。首次峰值内存取首遍后 VmHWM（KiB ÷ 1024），不能与 app PSS 相减。
- 同配置回归比较必须使用同一台设备、系统版本、模型/词表/shortlist/前缀表、语料、编译工具链、harness、CPU 亲和性和参数。不同手机分开建基线。
- 记录起止温度与频率上限。起跑前等待恢复；门槛超时就中止，保留部分结果。它不等于锁定实际 CPU 频率。
- 已用于报告的失败、超时和译文变化样本保留，不能当成零耗时。性能通过不代表质量通过；另跑哈希与必要的质量评测。

### 扩展评测

沿用[报告模板](TEMPLATE.md)，缺失项标为未测、不支持或失败。新增设备、场景或指标时升级测试清单，保留已有场景的定义与原始数据。模型、语料或计时口径变化后，为当前版建立新的原始基线并标记与旧版不可直接比较；不自动重跑两个版本。只有明确请求对照实验时才新增配对测量。

## 新增一次测量

完整构建、设备文件准备、运行命令见 [工具说明](../../tools/version-bench/README.md)。默认运行 v2 完整七场景；指定 `--scenarios` 仅作探索，不能作为正式基线。每次使用新的输出文件名，不覆盖已归档结果。新版本目录按上文结构建立：

```text
benchmark/data/vX.Y.Z/
  README.md      # 与上个版本的差异
  index.json     # 测量项与数据位置；共用的采集程序和语料在此登记别名
  raw/<device>/<评测>/
  checks/ + verify.py
```

本地代码用 `--working-tree-version v0.5.0` 命名快照，工具记录 HEAD、未提交状态和原生源码摘要，不要求先提交或打 tag。发布前再核对最终 tag 与被测源码，不能只改 JSON 中的版本名。

## 回归检查

```bash
python3 tools/version-bench/check.py baseline.json candidate.json \
  --baseline-version v0.3.0 --candidate-version candidate
```

同一份配对报告也可作为两个文件参数。检查器先核对测试清单 ID/摘要、对应版本的完整场景清单和固定重复协议；即使双方同时漏掉同一场景，也不能通过。输出以首次/热态速度（条源文/秒、倍率、变化百分比）展示，并附原始耗时。判定仍沿用原门槛：首次/热态耗时和峰值 RSS 任一增加 **超过 10%** 则失败；耗时 +10% 等价于速度约 −9.09%，没有将它悄悄改成速度 −10%。可用 `--latency-pct`、`--memory-pct` 调整。三个耗时/RSS 样本的极差超过中位数 10%，或起跑电池温度范围超过 3°C，标记为需复查，不给通过结论，也不自动触发补测。阈值是初始报警线，不是统计显著性检验，也不保证检出小幅回归。

退出码：`0` = 条件匹配且未越线；`1` = 性能越线或稳定译文哈希变化；`2` = 数据不完整、崩溃、条件不匹配或噪声过大。**1 和 2 都应阻止将这次结果标为验收通过。**

现有历史 JSON 原样保留，部分缺少设备、模型或构建指纹，检查器会返回 `2`。这些旧档保留其限制；从后续明确采集的当前版本建立完整自动回归基线，不自动补测旧版，也不凭空补写历史元数据。共享 CI 仅运行检查器单元测试；真机性能验收需在固定设备上手动运行，尚未接入自动设备流水线。

各版本的离线复核入口：

```bash
python3 -B benchmark/data/v0.3.0/verify.py
python3 -B benchmark/data/v0.5.0/verify.py
```

复核通过只表示归档内部一致，不重跑设备或评分模型，也不把已记录的验收失败改成通过。
